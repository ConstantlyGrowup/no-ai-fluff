# no-ai-fluff：交付前过一遍“说人话”审校

适用于：用户说“用 no-ai-fluff 过一遍 / 定稿 / 改成大白话”，或者你写完一篇面向人类阅读的中文长回复、要落盘的 `.md` / `.html`。

## 定稿流程

1. 调用 MCP 工具 `prepare_rtt_draft`：传草稿全文 `text`、用户的原始问题 `question`（有的话）、出口 `exit`（写文件用 `file`，否则 `terminal`）。
2. 如果返回 `status=needs_domain_triage`：判断列出的几句是否出自技术/工程语境，带 `draft_id` 和 `domain_triage` 再调一次 `prepare_rtt_draft`，取回审校规则。
3. 按返回的规则，对照原文和往返参考稿，只给读着费劲的句子写局部 JSON 补丁（`find` 必须是原文片段）；没有要改的就传 `[]`。
4. 调用 `finalize_patched_delivery(draft_id, patches)`。返回内容里 `---` 之前是定稿，`---` 之后是补丁统计和给你的交付说明，那部分不要写进交付物。
5. 把定稿原样交给用户，不要再自己润色。

宿主支持子智能体时，可以把第 1～4 步交给子智能体在独立上下文里做，但子智能体也必须走这两个 MCP 工具，不能自己直接重写全文。审校请用高推理强度。

## 交付后的一句提示（只在聊天里说）

- 终端回复（`exit=terminal`）：先原样发出定稿正文，正文结束后空一行、加一条分割线，再附上这句：

  > {{NOTE}}

- 落盘文件（`exit=file`）：这句提示**绝对不要写进目标文件**，文件里只有干净的定稿。在聊天里报告写到了哪个文件之后，再附上这句提示。

## 用户点名重写时：整段重写兜底

用户在定稿之后说“第 2 段重写”“这几句还是太绕，整段重写”，或者直接贴出几句话让你重写时，由你直接重写，不再调用 MCP 工具。这一步不再是局部小改，可以整段重组语序，但必须守住下面七条：

{{RULES}}

重写完只发出改好的那一段（或那几句），并说明改的是哪一段；如果交付物是文件，只替换文件里的那一段。

前提：已在当前 agent 里注册 MCP Server（stdio，命令 `no-ai-fluff`，参数 `mcp`），并在环境变量或 `.env` 里配置了 `OPENROUTER_API_KEY`（读不到时自动改用 `TENCENTCLOUD_API_KEY`）。
